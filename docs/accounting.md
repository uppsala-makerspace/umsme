# Accounting Support (Bokföringsstöd)

## 1. Overview

The treasurer books roughly 2000 transactions a year, most of them by hand.
About 95% of those are things UMSME already knows about: membership payments,
expense reimbursements, and standard income such as clay or course fees. The
accounting support turns UMSME into the source system for those transactions
and generates the bookkeeping material, so the treasurer only handles the
remainder manually.

From an uploaded bank statement, UMSME produces **two files** that the
treasurer imports into the bookkeeping system (Spiris) themselves:

1. A **SIE 4i file** with ready verifications for the transactions UMSME
   recognizes.
2. A **remaining CSV** with the transactions UMSME does *not* recognize, in
   the exact same format as the uploaded statement, for manual entry ("the
   5%").

There is no direct integration with Spiris (no API, no integration license).
Receipts stay where they already live (Google Drive), with a link in the
verification text. Everything runs in the **admin** app; the member PWA is
not involved.

## 2. Transaction Categories and Verification Series

Every transaction belongs to one of four categories, each with its own
verification series. Series are separated by *source/lifecycle*, not for
analysis (analysis is done with accounts and dimensions). Separate series
allow a category to be cleanly deleted and re-imported in Spiris without
touching the others — see section 9.

| Category            | Series | Source of truth                              | Output   |
| ------------------- | ------ | -------------------------------------------- | -------- |
| Expense reimbursements | `U` | Expenses collection (status `reimbursed`)    | SIE      |
| Member payments (Swish) | `M` | Payments collection                          | SIE      |
| Standard income (clay, courses…) | `S` | Payments collection + configured codes | SIE  |
| Everything else (rent, insurance, Bankgiro/PG…) | `K` | Not in UMSME | remaining CSV |

Series `K` is configured in Spiris, not generated by UMSME — the treasurer
books those rows manually from the remaining CSV.

## 3. Design Decisions

- **Cash method (kontantmetoden).** An expense is booked as a single
  verification at reimbursement, dated when the money moved.
- **Not VAT registered.** No VAT codes appear in the verifications.
- **Stateless processing.** The bank export reads from the database but
  **writes nothing** and keeps no record of previously processed statements.
  The process is a pure function: `bank CSV → (SIE, remaining CSV)`. Running
  the same statement twice gives the same output twice. Protection against
  double booking is handled *outside* the system: the treasurer uploads
  non-overlapping statements, and the bank-account balance reconciliation in
  Spiris catches mistakes. This is a deliberate decision, not an omission —
  do not add persistence/idempotency/deduplication of processed statements.
- **Empty verification numbers.** A verification is identified by series +
  number, and the law requires each series to be unbroken — but that
  requirement applies to the *final bookkeeping in Spiris*, not the transfer
  file. UMSME leaves the number empty in `#VER`; Spiris assigns numbers into
  its own unbroken series on import. UMSME must not keep its own counter
  (stateless processing would make it produce collisions or gaps).
- **Configuration lives in `settings.json`** (section 5), not in the
  database and not hard-coded.

## 4. Data Model

### Expense accounts carry dimensions, not account numbers

An **expense account** (`expenseAccounts` collection) is a category a member
picks when submitting an expense — e.g. "Tools" or "Consumables". It has
`name`, `explanation`, and a `dimensions` map, but deliberately **no ledger
account number**: the actual BAS account is chosen per expense by the
treasurer (below).

An account also carries `groupIds` and `approverMemberIds` — who may spend on
it and who approves — but those affect access only, never the generated
verifications; see [expenses.md](expenses.md) §3.

The `dimensions` field maps dimension number → object code, e.g.
`{ "1": "VERKSTAD" }`. The allowed dimensions come from
`settings.accounting.dimensions` (typically `1` = cost center, `6` =
project). Object codes end up as SIE `#OBJEKT` keys, so the admin form trims
whitespace and strips quotes; the form offers typeahead over object codes
already used on other expense accounts (native `<datalist>`).

### Per-expense bookkeeping fields

Two optional fields on the `expenses` collection, set when the treasurer
marks an expense reimbursed:

| Field                | Meaning                                                    |
| -------------------- | ---------------------------------------------------------- |
| `bookkeepingAccount` | The BAS ledger account chosen from `settings.accounting.expense.accountOptions` |
| `reimbursedDate`     | The actual payment date (editable; defaults to today). This is the verification date under the cash method — distinct from the `reimbursedAt` audit timestamp. |

The account choice is gated structurally: it exists only in the treasurer's
reimburse action (roles `treasurer`/`admin`), only for expenses in status
`confirmed`, and is validated server-side against the configured options. It
cannot be set from the member app or by the board's confirm step. Undoing a
reimbursement keeps both fields as a remembered default for the redo.

Expenses reimbursed **before** these fields existed have neither and can
never be matched by the bank export; the diagnostics point them out
(section 8).

## 5. Configuration

Everything lives under `accounting` in the admin app's `settings.json`
(template in `admin/example-settings.json`):

```json
"accounting": {
  "company": { "orgNo": "000000-0000", "name": "Föreningen" },
  "bankAccount": "1930",
  "matchWindowDays": 5,
  "dimensions": [
    { "nr": 1, "name": "Kostnadsställe" },
    { "nr": 6, "name": "Projekt" }
  ],
  "expense": {
    "series": "U",
    "accountOptions": [
      { "account": "5010", "name": "Lokalkostnader" },
      { "account": "6110", "name": "Kontorsmateriel" }
    ]
  },
  "memberPayment": { "series": "M", "account": "3110", "dimension": { "1": "MEDLEM" } },
  "standardIncome": {
    "series": "S",
    "codes": [
      { "code": "LERA", "account": "3010", "dimension": { "6": "VERK" } }
    ]
  }
}
```

| Key | Meaning |
| --- | --- |
| `company` | Written to the SIE header (`#ORGNR`, `#FNAMN`) |
| `bankAccount` | The BAS account the bank statement represents; the bank leg of every verification |
| `matchWindowDays` | ± days allowed between a bank row's transaction date and the database date (default 5) |
| `dimensions` | The allowed dimensions; drives the expense-account form and SIE `#DIM` names |
| `expense.accountOptions` | The BAS accounts the treasurer can pick between when reimbursing |
| `memberPayment` | Account (and optional dimension) all membership payments are credited to |
| `standardIncome.codes` | Code → account (+ optional dimension) mappings; each entry **must** be an object with `code` and `account` — the method rejects malformed entries with a clear error |

The client never reads `Meteor.settings` directly; the role-gated method
`accounting.config` returns the subset the admin UI needs.

## 6. The Bank Export Page

`/accounting/bankexport` in the admin app (menu: *Accounting → Bank export*;
roles `treasurer`/`admin` for processing).

1. **Upload** a transaction report CSV exported from Swedbank. The expected
   format is: Latin-1/CP1252 encoding, a comment line, then a column header
   line (`Radnr,Clnr,Kontonr,Produkt,Valuta,Bokfdag,Transdag,Valutadag,Referens,Text,Belopp,Saldo`).
   Matching uses `Transdag` (the transaction date; `Bokfdag` can lag).
2. **Review the summary**: per-category counts and sums, the candidate pools
   considered, flags for rows needing attention, per-row diagnostics for near
   misses, and the control identity
   `Σ(all bank rows) = Σ(SIE bank legs) + Σ(remaining CSV)` with an
   OK/MISMATCH label.
3. **Download** the SIE file and the remaining CSV.

## 7. The Matching Engine

Rows are processed in file order. Every bank row matches at most one database
document and every document is consumed at most once.

### a) Outgoing rows (`Belopp < 0`) → expense reimbursements (series `U`)

Candidates are expenses with status `reimbursed` and a `bookkeepingAccount`,
where the amounts are equal and `Transdag` is within `matchWindowDays` of
`reimbursedDate`. The verification is **debit `bookkeepingAccount` / credit
`bankAccount`**, dated `Transdag`, with the expense account's dimension
objects on the debit leg and a text containing the expense id and the Google
Drive receipt link.

A reimbursed expense *without* a bookkeeping account cannot be booked; its
bank row stays in the remaining CSV with a flag (the treasurer forgot to pick
an account).

### b) Incoming Swish rows (`Belopp > 0`, `Text` starts with `Swish `)

The payer's phone number is extracted from `Text` and compared against
`payment.mobile` after normalization (strip non-digits, compare the last 9
digits — unifies `46701234567`, `+46 70 123 45 67`, `0701234567`).
Candidates must also match on amount and date window.

**Both payment sources are evidence**, and they cover disjoint transactions
(so no duplicates arise):

- **Swish-callback payments** (the automatic Swish number): created by the
  payment app when Swish Handel confirms; carry `member`, `initiatedBy`, and
  a `pt:<paymentType>` code in the message. The bank sync deliberately skips
  this number (`automaticSwishNumber` in settings).
- **Bank-synced payments** (the manual Swish number, `hash` set): imported by
  the admin bank sync and manually linked to a member/membership in the
  Payments view.

A found payment is then classified:

| Classification | Rule | Verification |
| --- | --- | --- |
| Standard income (`S`) | The message contains a configured code as a whole word (case-insensitive) or as `pt:<code>` | debit bank / credit the code's account, with its dimension |
| Member payment (`M`) | App-initiated (`initiatedBy` + `member` + `pt:`), **or** manually linked (`member` + `membership` set) | debit bank / credit `memberPayment.account`, with its dimension |
| Unclassifiable | Neither of the above | stays in remaining CSV, flagged, with a diagnostic suggesting the fix |

Standard income codes are matched **heuristically** from Swish messages
during a transitional phase — a controlled flow may replace this later. This
is why standard income has its own series: it is the stream most likely to
need a redo (section 9).

### Multiple candidates

If several payments fit one bank row, they are matched anyway **when they
are interchangeable** — same classification (same income code, or the same
member's membership payment). This covers e.g. one person buying two packets
of clay the same day: the verification is identical whichever payment is
picked, so the one closest in date is consumed and the rest are left for
subsequent rows. If the candidates *conflict* (different codes, or a code
vs. a membership), the row stays unmatched with an `ambiguous-payment` flag
listing what the candidates claimed.

### d) Everything else → remaining CSV

Aggregated Bankgiro/PG deposits, rent, autogiro, direct supplier payments,
and Swish rows without a counterpart in the payments table all pass through
untouched.

## 8. Diagnostics

When rows unexpectedly fail to match, the summary explains why:

- **Candidate pools**: how many reimbursed expenses were considered (and how
  many lack a reimbursement date or bookkeeping account), how many
  Swish-callback vs. bank-synced payments.
- **Per-row near misses**, e.g.:
  - *"expense … has the right amount but no reimbursedDate (reimbursed before
    phase 1?)"*
  - *"payment … fits but is unclassifiable — link it to a member/membership in
    the Payments view, or add its code to accounting.standardIncome.codes"*
    (with the Swish message shown)
  - *"payment with matching number+amount exists but the date is N days off"*

The workflow this enables: upload → read the diagnostics → fix the data
(link payments, add codes, pick bookkeeping accounts) → upload the same file
again. Statelessness makes the loop safe to repeat.

## 9. Recovery and Re-import

The separate series exist so one stream can be redone in isolation — e.g.
"something was wrong with all standard income January–March": delete series
`S` for the period in Spiris and re-import, without touching `M` or `U`.

- Deletability is governed by whether the period is **locked in Spiris**:
  unlocked → delete + re-import (Spiris renumbers); locked → correct with
  reversal entries instead.
- Since the association is not VAT registered there are no early forced
  period locks; lock periods deliberately once they are reconciled.
- The re-import flow (a consequence of statelessness): re-export the bank
  statements for the period from the bank, fix the heuristics/configuration,
  rerun the bank export in UMSME, delete the old series batch in Spiris, and
  import the new file. Being able to retrieve old bank statements again is a
  prerequisite.

## 10. Output Formats

### SIE file

Encoding **PC8 / codepage 437** (per the SIE standard), CRLF line endings.
Header: `#FLAGGA 0`, `#PROGRAM`, `#FORMAT PC8`, `#GEN`, `#SIETYP 4`,
`#ORGNR`, `#FNAMN`. `#DIM`/`#OBJEKT` are declared only for dimensions and
objects actually used. One `#VER` per matched transaction with an empty
verification number and balanced `#TRANS` rows (the builder throws on
imbalance); object lists use the `{nr "object"}` syntax on tagged rows.

```
#VER "M" "" 20260621 "Medlemsbetalning Alice (memberBase)"
{
   #TRANS 1930 {} 350.00
   #TRANS 3110 {1 "MEDLEM"} -350.00
}
```

### Remaining CSV

Byte-faithful to the upload: the original header lines plus the unmatched
rows' original lines verbatim, re-encoded to CP1252 with the original line
endings. It can be uploaded straight to Spiris.

## 11. Code Map

| Path | Contents |
| --- | --- |
| `admin/imports/accounting/bankFile.js` | CP1252 decode, quote-aware CSV parsing, remaining-CSV rebuild |
| `admin/imports/accounting/match.js` | The pure matching engine, classification rules, diagnostics |
| `admin/imports/accounting/sie.js` | Verification composition and SIE 4i generation (CP437) |
| `admin/server/methods/accounting.js` | `accounting.config` and `accounting.processBankFile` (role-gated; the only DB access) |
| `admin/client/ui/accounting/` | The bank export page (`BankExport` template) |
| `admin/tests/accounting.tests.js` | Unit tests for parsing, matching, and SIE generation (`npm test` in `admin/`) |

The three `imports/accounting/` modules are pure (no Meteor dependencies
beyond `iconv-lite`), which is what makes them unit-testable and runnable
outside Meteor.
